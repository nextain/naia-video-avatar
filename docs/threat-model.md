# Threat Model and Limitations

English | [한국어](./threat-model.ko.md)

> This document explicitly states **what the self-trust harness prevents and what it cannot prevent**.
> Core principle: Local hooks provide *warnings and friction*; the **final trust boundary is remote CI**.

## 1. Trust Boundary

| Tier | Role | Bypass Potential |
|------|------|------------|
| **Local Hooks** (Claude Code PreToolUse) | Primary friction & instant feedback | **High** — `--no-verify`, `bash echo > file`, `python -c open().write()`, direct editing of hook files, spoofing `HUMAN_APPROVED_CHARTER_EDIT=1` env |
| **Remote CI** (GitHub Actions) | **Final line of defense** — recalculates entire changeset | Low — provided **branch protection / rulesets are enforced** (Section 6 below) |

As long as the AI has local file write permissions, local hooks do not constitute a security boundary. While referred to as "two-layer defense", **enforcement authority rests entirely with CI**.

## 2. What Is Prevented (at the CI Level)
- **Completion evidence forgery** — Files referenced by `Verified:/Evidence:` must *actually be included in the current diff* (preventing the reuse of existing files).
- **Unregistered structure creation** — Blocks root paths outside the F12/F13 registries.
- **Unmet SDLC gates** — Blocks source changes that lack deliverables required by `change_set_rules`.
- **Unauthorized modification of hooks/workflows/charter** — `ci-verify-charter` blocks changes that lack human approval (via the `charter-approved` label).

## 3. What Cannot Be Prevented (Honest Limitations)
- **AI "reading instructions but failing to follow them"** — Disregarding instructions cannot be defended against solely by code (human review is required).
- **Deliverables themselves are generated by AI** — When evidence consists of code or test suites, that code is also AI-generated. The *veracity* of evidence cannot be guaranteed on its own → it must be supplemented with mutation testing, external corpora, and human sample reviews.
- **Local environment variable spoofing** — `HUMAN_APPROVED_CHARTER_EDIT=1` can be set directly in local environments. CI's `CHARTER_APPROVED` check (based on maintainer labels) remains definitive.
- **Self-hosted runner tampering** — Running verification on machines accessible to the AI creates a self-verification paradox. GitHub-hosted runners are strongly recommended.

## 4. Known Residual Risks (Roadmap)
- **Symlink realpath not handled** — Protected paths could potentially be disguised using symlinks. Reinforcing path resolution with `fs.realpathSync` in CI is planned.
- **Simplified glob implementation** — `globToRe` supports only `*`, `**`, and `{a,b}`. Nested braces and character classes are unsupported → introducing `picomatch` is under consideration.
- **Circular verification** — All 89 self-tests were written by the implementers themselves. Integration tests against external heterogeneous repository corpora are required.
- **Tool dependencies** — Assumes Node.js, Claude Code hooks, and GitHub Actions. Decoupling core verifiers into standalone CLIs and converting hooks into adapters is planned on a separate track.

## 5. Threat Actor Assumptions
The baseline assumption is not that "AI makes mistakes", but rather that **"AI may re-interpret or bypass policies to achieve objectives"**. Therefore, policies and evidence are recomputed in zones inaccessible to AI (CI), and evidence must be re-executable.

## 6. Mandatory Operational Prerequisites (Without Which CI Enforcement Fails)
- GitHub branch protection / ruleset:
  - Required status check = `self-trust gates`
  - **Do not allow bypassing** (strict enforcement, prohibiting bypasses even for administrators)
  - Pull requests required (direct pushes to main prohibited)
- The `charter-approved` label must be granted **by maintainers only**.
- Because these prerequisites cannot be enforced via repository code alone, they must be applied via configuration scripts (`gh api` / Terraform) and verified using checklists when adopting the template.

# Threat Model and Limitations

English | [한국어](./threat-model.ko.md)

> Honestly states **what the self-trust harness prevents and what it cannot prevent**.
> Core principle: Local hooks provide *warnings and friction*; the **final trust boundary is remote CI**.

## 1. Trust Boundary

| Tier | Role | Bypass Potential |
|------|------|------------|
| **Local Hooks** (Claude Code PreToolUse) | Primary friction & instant feedback | **High** — `--no-verify`, `bash echo > file`, `python -c open().write()`, direct editing of hook files, spoofing `HUMAN_APPROVED_CHARTER_EDIT=1` env |
| **Remote CI** (GitHub Actions) | **Final line of defense** — recalculates entire changeset | Low — provided **branch protection / rulesets are enforced** (Section 6 below) |

As long as the AI has local file write permissions, local hooks do not constitute a security boundary. While referred to as "two-layer defense", **enforcement authority rests entirely with CI**.

## 2. What Is Prevented (CI Standards)
- **Completion evidence forgery** — Files referenced by `Verified:/Evidence:` must *actually be included in the current diff* (preventing reuse of existing files).
- **Unregistered structure creation** — Blocks root paths outside F12/F13 registries.
- **Unmet SDLC gates** — Blocks source changes without deliverables required by `change_set_rules`.
- **Unauthorized modification of hooks/workflows/charter** — `ci-verify-charter` blocks changes without human approval (`charter-approved` label).

## 3. What Cannot Be Prevented (Honest Limitations)
- **AI "reading but not following"** — Ignoring instructions cannot be defended against by code (requires human review).
- **Deliverables themselves generated by AI** — If evidence consists of code/tests, that code is also AI-generated. The *veracity* of evidence cannot be guaranteed → must be supplemented by mutation tests, external corpora, and human sample reviews.
- **Local env spoofing** — `HUMAN_APPROVED_CHARTER_EDIT=1` can be set directly in local environments. CI's `CHARTER_APPROVED` (maintainer-label based) is final.
- **Self-hosted runner tampering** — Verifying on machines accessible by AI creates a self-verification paradox. GitHub-hosted runners are recommended.

## 4. Known Residuals (Roadmap)
- **Symlink realpath unhandled** — Protected paths could be mimicked via symlinks. `fs.realpathSync` reinforcement planned in CI.
- **Basic glob implementation** — `globToRe` supports only `*`, `**`, and `{a,b}`. Nested braces and character classes unsupported → considering `picomatch`.
- **Circular verification** — All 89 self-tests were written by implementers. Integration tests against external heterogeneous repo corpora required.
- **Tool dependency** — Assumes Node.js, Claude Code hooks, and GitHub Actions. Decoupling core verifiers into CLIs and turning hooks into adapters is on a separate track.

## 5. Threat Actor Assumptions
The baseline assumption is not that "AI makes mistakes", but rather that **"AI may re-interpret or bypass policies to achieve objectives"**. Therefore, policies and evidence are recomputed in zones inaccessible to AI (CI), and evidence must be re-executable.

## 6. Mandatory Operational Prerequisites (Without Which CI Enforcement Fails)
- GitHub branch protection / ruleset:
  - Required status check = `self-trust gates`
  - **Do not allow bypassing** (strict, even for administrators)
  - PR required (direct push to main prohibited)
- The `charter-approved` label must be granted **by maintainers only**.
- Because these prerequisites cannot be enforced via repository code alone, they must be applied via setup scripts (`gh api` / Terraform) and verified via checklists when adopting the template.

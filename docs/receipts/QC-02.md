## 4. Findings

### Blocking (the documents promise a behaviour that does not work)

None found. Every behaviour promised by PC section 4 (invariants 1-4) and SP sections 3 and 4 that could be exercised with the provided samples and hostile inputs behaved as written, including: all path-hostile ZIP entries and every size / count limit rejected with the `Blocked:` message (and inclusive boundaries accepted), previous avatar cleared and controls disabled on error, no network activity after load, bundle files never executed or played unless referenced, automatic return to idle after speech / action, Stop with no stale-event overwrite, last-load-wins under rapid or racing loads, and the sample-catalog failure message with a working file picker.

### Nonblocking (wording, convenience, robustness)

1. **Status / error text is below the fold on a 1440x900 window.** The status box (the only place errors appear) sits at about y=1029 px while the viewport is 900 px high, so a `Blocked:` message after choosing a bad file is not visible without scrolling. This matches the SP wireframe (status at the bottom of the panel) but is poor in practice. The status also has no `role` / `aria-live`, so assistive technology is not told about changes. (Screenshot: `desktop-error-blocked.png`.)
2. **Status text contrast is 1.84:1** (colour #aebbd0 on a near-white panel), far below the 4.5:1 AA guideline (M-07, visible in `mobile-390-loaded.png`). The error colour #ff8d8d is similarly light on white.
3. **Changing the background colour silently removes a chosen background image** (B-05). SP says the colour input "updates the stage background colour" and Clear "restores the active solid colour", which implies the two can coexist; SP does not say the image is dropped.
4. **Misleading reason for an empty file.** A 0-byte file reports "Blocked: NVA bundle exceeds the 100 MiB limit" (E-01).
5. **Error text language and detail.** Reasons mix English and Korean, and some expose raw parser text, for example a JSON parser message or "nva_version: undefined" (E-16, E-17). SP only requires `Blocked: <reason>`.
6. **A very long unbroken avatar name breaks the mobile layout.** A 3000-character name gives a 21714 px wide page at 390 px (M-04, `mobile-390-longname.png`). The status text does not wrap.
7. **Background colour is applied about 200 ms after the input event, not in the same tick** (B-01). This looks like a CSS transition; "real time" is satisfied.
8. **Cosmetic differences from the wireframe**: empty dropdown placeholders read "No speech videos loaded" / "No packaged speech videos" instead of the wireframe's "Select ... clip"; a stale `aspect-ratio` style stays on the empty video after a blocked load; the header says "NVA v0.3" while every menu sample is a 0.2-era bundle; the action-complete path shows "Playback complete; idle restored." although SP specifies that text only for speech.
9. **Not verifiable from the outside**: which clip the talking loop uses when a bundle has several (SP: scenario start animation first, otherwise manifest order). In sample 1 the talking and idle animations reuse the same clip bytes, so the clip choice cannot be distinguished. Only the enabled state, status, muted and loop flags were checked (T-01..T-04).

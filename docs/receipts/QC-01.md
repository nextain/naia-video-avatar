## 4. Findings

### 4.1 Blocking (behaviour promised by SP does not happen)

**B1. A failed load after a good avatar leaves playback controls partly enabled, and Stop revives the old avatar.**
SP §3 (file picker) says controls are disabled at the start of a load, and SP §4 says that on an invalid bundle "Playback controls remain disabled".
Observed (T-RECOVER, T-BLOCK-AFTER-GOOD-404, T-BLOCK-AFTER-GOOD-STOP): open any valid sample, then choose a non-ZIP file (or pick a sample whose fetch returns 404). The status correctly shows `Blocked: …`, the three play buttons are disabled, but the speech dropdown, the action dropdown and **Stop and return to idle** stay enabled. The previous avatar stays frozen on the stage; clicking Stop restarts the old avatar's idle loop and overwrites the Blocked message with `Stopped; idle restored.` The user is left looking at an avatar that is not the one they asked for, with a status that no longer says why. From a clean start (no earlier good load) all controls are correctly disabled (all 33 fresh-state T-BLOCK-* tests pass), so the defect is limited to the blocked-after-good path. Screenshot: `shot-stop-after-blocked.png`.

### 4.2 Non-blocking

**N1. Superseded `play()` calls are reported as failures under extreme click bursts.** When 200 programmatic clicks are dispatched inside one task (T-BURST*), the final status is `Speech video failed: The play() request was interrupted by a new load request.` (or `Talking failed: …`) even though the last click was Stop / Play. The video itself ends in a consistent muted idle state and no uncaught error occurs. With real mouse/tap clicks at 0, 10, 30, 60, 100 and 200 ms gaps, double clicks, and 15x play/stop alternation (T-RAPID-*, `probe3.log`), the final state and status were always correct, so this is an edge case that a human cannot normally produce. Still, a superseded request should not be shown to the user as a failure.

**N2. Low contrast of the status box.** Computed colours: normal status text about 1.9:1 against its box background and the SP-specified alert colour `#ff8d8d` about 2.3:1 (12px text). The SP mandates the alert colour, so this is a design point rather than a deviation. Visible in `shot-load-studio4-M.png` and `shot-error-empty-M.png`.

**N3. Wording and wireframe differences.**
- Status reads `N packaged speech videos` (SP: `N speech videos`).
- Speech label reads `Pre-rendered speech video` (SP wireframe: `Pre-rendered speech`).
- Empty dropdowns read `No speech videos loaded` / `No actions loaded`; the wireframe shows `Select speech clip...` / `Select action...`.
- Singular is not handled (`1 packaged speech videos`, `1 actions`).

**N4. Not every non-looping clip becomes an action.** Sample 1 has five non-looping clips but lists three actions (`dance`, `wave`, `nod`); the two pose-transition clips are not offered. SP does not define which clips count as actions, so this is recorded for the owner to confirm (observation `T-LOAD-demo-*-actions`).

**N5. Talking-loop enablement rule is looser than the SP sentence.** SP says the button is enabled when a v0.2 bundle "contains a `talking` clip". Samples 1 and 2 have no clip named `talking` but do have talking-capable clips, and the button is enabled for them. Playing works. The SP sentence should say which clips qualify.

**N6. Integrity and input hardening not described in PC/SP (observations).**
- A bundle whose clip bytes no longer match the manifest hash still opens as `Ready` (T-HASH). PC invariant 5 mentions verification integrity, but no hash rule is specified.
- A text file renamed `.png` is accepted as a background image: no error, the stage just shows an empty image layer (T-BG-NONIMAGE). The player keeps working.
- Background colour persists across bundle loads (T-BG-PERSIST); SP does not say.

**N7. Background colour change is animated** with a CSS transition of a few tenths of a second; "real time" in SP is satisfied visually, but a script reading the colour immediately sees the old value.

### 4.3 Things that matched PC/SP (highlights)

- All six samples open on desktop and phone with the exact `Ready · … ` status structure, correct aspect ratio, and a muted, looping, advancing idle.
- Speech, talking loop, action and Stop transitions and status strings match SP exactly, including automatic return to idle with `Playback complete; idle restored.`
- All 31 malformed or unsafe inputs (2 repeated on phone) are rejected with `Blocked: <reason>` in the SP alert colour, including every unsafe ZIP path form, 513/520 files, oversized manifest, oversized archive and zip-bomb expansion; exactly 512 files is accepted. Unreferenced hostile files inside a bundle were never executed.
- Media failures and catalog failures produce the SP error strings and recover; the file picker stays usable after catalog failures.
- Stale loads (slow sample arriving after a newer file, after a newer error, or out of order) are discarded; 13 rapid sample clicks end on the last choice.
- No network request after a local file is opened and every control is used; Blob URLs of the previous bundle are revoked on the next load and do not accumulate.
- Phone layout (390 and 320 wide) has no horizontal scroll, panel above the stage, stage at least 460px high; the 820/821px breakpoint is correct.
